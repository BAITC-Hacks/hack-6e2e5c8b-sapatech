## Первый запуск и расписание

1. Проверить корень Git, origin, ветку, автора и незакоммиченные правки.
   Существующую работу сохранить; ничего не сбрасывать и не переключать при dirty tree.
2. Выполнить `git fetch origin`. Проверить успешный код возврата.
3. Прочитать свежие файлы без checkout/pull чужой ветки:

```text
git show origin/feat/T-03-nursultan-agent:coordination/CONTROL.md
git show origin/feat/T-03-nursultan-agent:coordination/MAILBOX.md
git show origin/feat/T-03-nursultan-agent:coordination/inbox/ROLE.md
```

В последней команде ROLE заменить точным именем своей роли из таблицы.
Для PLAN, HACKATHON, contracts, decisions и карточки T-06 также можно использовать
`git show`: отсутствие новых файлов на собственной старой ветке не блокирует чтение.
Для выполнения использовать собственную ветку; код интеграции проверять в отдельной
копии/временном worktree фиксированного commit, не перезаписывая свою рабочую копию.
Если нужной локальной ветки нет, использовать существующую origin-ветку; только
новую review/T-06 создавать от origin/feat/T-03-nursultan-agent.

4. Создать или обновить ОДНО расписание текущего чата каждые 3 минуты.
   Проверить ранее созданные Beeline-расписания своей роли, не плодить дубликаты.
   Не создавать новый чат на каждом запуске, cron/sleep-цикл или расписания коллег.
   Зафиксировать фактический Automation-ID и подтверждённый статус в отчёте.
   Если инструмент недоступен, сообщить об этом: не утверждать, что расписание включено.
5. Сразу выполнить первую проверку очереди; не ждать первого таймера.

## Каждый запуск

1. Проверить status/branch, fetch; не вмешиваться в чужие или незавершённые правки.
   При ошибке fetch не принимать новые задания и не считать отсутствие файлов stop.
2. Сначала CONTROL. Mode=stop приоритетнее любых inbox и старой работы.
3. Сверить `(Message-ID, Revision)` с собственным опубликованным отчётом и локальным
   `jobs/mailbox/ROLE.json` (путь игнорируется Git). Фиксировать claim до долгой работы.
   Опубликованный отчёт — общее свидетельство; локальный файл — защита до commit.
4. Вести только одно активное задание. Статус in_progress означает продолжить с
   сохранённого места, а не начать заново. needs_review уже передан координатору:
   повторно не исполнять до новой revision. blocked перепроверять только при новых
   входных данных. Уровень requested/accepted в RECEIPTS не повод повторять тесты.
5. Если в момент таймера уже работает та же сессия, не создавать второго исполнителя.
   При обновлении CONTROL/inbox во время работы перечитать их перед публикацией.
   Новое задание не уничтожает старые правки; при противоречии зафиксировать блокер.
6. Выполнить только свою область задачи и её проверки. Не запускать полный набор
   при каждом тике. Не менять official scorer; не обращаться к платным API.
7. Обновить отчёт при начале, существенном результате, блокере или завершении.
   Commit/push только своей ветки и только перечисленных файлов (без `git add .`).
   При non-fast-forward сохранить работу и сообщить блокер, не force-push/rebase/reset.
   Перед commit проверить diff и автора; после push сверить remote hash.
8. Кратко ответить в чате; главным результатом остаётся опубликованный отчёт.
   При отсутствии изменений — короткий idle, без пустых коммитов и повторных прогонов.

## Формат ответа

Один Markdown-файл на пару ID/revision; обновлять его, сохраняя этапы в журнале.
Code-commit записывать фактическим hash проверенного кода; если есть новые изменения,
сначала их проверить и закоммитить, затем отдельным коммитом добавить отчёт с hash.
Для документационного результата Tested-commit может быть исходным проверенным hash.
Не пытаться вставить hash отчётного коммита в него самого: Нурсултан получает его из Git.

```text
Message-ID: B1-001
Revision: 1
Role: BAUYRZHAN_CORE
Task: T-04
Status: in_progress | needs_review | blocked | stopped
Automation-ID: фактический id или unavailable
Automation-state: ACTIVE | deletion_pending | DELETED | unavailable
Source-commit: hash прочитанного сообщения координатора
Tested-commit: hash проверенного кода
Working-branch: feat/T-04-bauyrzhan-strategy
Updated: дата/время с часовым поясом

Result: что выполнено; что ещё не выполнено
Files changed: точные пути
Validation: реальные команды, exit codes, итог, среда
Findings: важность, владелец, файл:строка, воспроизведение и влияние
Known limitation: подтверждённые ограничения
Integrator action: что должен принять/проверить Нурсултан
```

Не отмечать непроведённую проверку как passed. Не выдавать модельные выводы за
измерения. Findings могут быть пустыми: не придумывать ошибки ради отчёта.

## Приём координатором

Нурсултан fetch-ит три рабочие ветки, сравнивает их hash и отчёты с RECEIPTS и
`jobs/mailbox/coordinator.json`. Проверяет ID/revision, автора, owned paths, diff,
контракт, воспроизведение существенных находок и сфокусированные проверки.
Отчёт без опубликованного кода не подтверждает готовность этого кода.
В RECEIPTS фиксирует observed commit, tested commit, accepted/changes_requested/blocked,
доказательства и следующий шаг. Замечания публикует новой revision в inbox владельца.
Готовые T-04/T-05 объединяет в собственную ветку только при чистом дереве, после
ревью, без squash. Reviewer-ветку читает через git show: её merge не требуется.
Проверка не означает автоматическое принятие всех обещаний или расширение scope.

## Завершение и удаление планировщиков

Когда итоговый код и артефакты прошли критерии готовности и проект объявлен завершённым
либо Нурсултан прямо дал stop, координатор публикует Mode: stop с новым Stop-ID.
Не объявлять проект сданным на платформе без реального подтверждения.

Получатель stop:

1. Прекращает брать задания; останавливается на ближайшем безопасном этапе, сохраняет
   незакоммиченные изменения. Не удаляет файлы и не коммитит непроверенный код ради stop.
2. Публикует в своём каталоге отчётов `STOP-ID.md`: Status=stopped, свои Automation-ID,
   состояние работы/незакоммиченных файлов, последние hash, что осталось, initially
   Automation-state=deletion_pending. Не задерживает остановку ради новых экспериментов.
3. Через инструмент приложения удаляет только своё расписание этой роли. При нескольких
   подтверждённых дублях этой роли удаляет и их. Не трогает другие автоматизации.
4. После подтверждения инструмента дописывает Automation-state=DELETED в этот же
   отчёт и commit/push отчёта в свою ветку, затем завершает ответ и работу.
   Если нет доступа к удалению или push, честно пишет блокер в доступном канале;
   не утверждает, что расписание удалено. Локальный STOP-флаг запрещает новые задания.

Координатор забирает три подтверждения DELETED, записывает итоги, публикует последний
коммит и удаляет своё beeline-3-2 (актуальный ID после подтверждённой замены
beeline-3 при передаче координатора). Если участник недоступен, сообщает, чьё подтверждение
не получено; удаление чужого расписания из этого аккаунта не обещает.
