# Нурсултан: координация, приёмка и сдача

Статус: предложение следующего этапа. Изменять CONTROL=stop и запускать работу
после решения оператора начать этот этап. [Общий план](README.md).

## Результат и модели

Одна выбранная и воспроизводимая версия в командном репозитории, соответствующий
ей CSV, понятная демонстрация и подтверждение отправки после разрешённой сдачи.

**GPT-6 Astra high** — ограниченное ревью математической гипотезы, конфликтов
в оценке результата и итогового diff. **GPT-6 Sol medium** — инструкции,
интеграция, команды и комплектность. Для трудного дефекта Sol high.
Сохранить резерв ресурса на последние ошибки; не включать Max/Ultra по умолчанию.
Не переносить вычисление бюджетных ограничений в LLM и не добавлять API в runtime.

Область: координация, shared docs, agent.py/setup при доказанном дефекте,
интеграция, общий submission.csv. README и evals делает Ерлан, strategy — Бауыржан.

## Первые 10 минут

1. Узнать фактический дедлайн и состояние формы отправки. План 90 минут не
   означает, что столько времени осталось. Сохранить последние 30 минут для сдачи.
2. Зафиксировать baseline `4272a0787248de1481fb6b45dfcbdecee1568ae4`, его CSV
   и зависимости. Сохранить возможность сдать именно его, без reset чужих веток.
3. После решения оператора начать этап выдать новые task/revision с владельцами,
   ветками и границами. Не переиспользовать старое STOP-сообщение как разрешение.
   Автоматические расписания для короткого этапа не нужны.
4. Передать Ерлану агрегаты нового аудита и план, Бауыржану — исходный hash,
   критерии принятия и временной лимит. Каждый отвечает за свою область.
5. Подтвердить новый контрольный диапазон и критерии ДО измерений кандидата.

## Пока коллеги работают

- Подготовить комплект уже рабочей версии и проверить доступ к репозиторию/форме.
  Не ждать нового алгоритма, чтобы выяснить, как сдавать.
- На Astra high проверить гипотезу Бауыржана: зачем платный пилот окупается;
  как он расходует лимиты; корректно ли переносится эффект; нет ли двойного
  multiplier или выбора коэффициента по удачному seed.
- Не переписывать strategy самому. Обнаруженный дефект возвращать Бауыржану.
- Проверить, что Ерлан сравнивает две ревизии в разных процессах/пакетах и
  фиксирует пути реально загруженных модулей. Иначе импорт strategy может
  сохраниться от первой версии и сделать сравнение недостоверным.
- Не менять агентскую оболочку без подтверждённой проблемы: её штатные проверки
  сейчас проходят, дополнительная архитектура не входит в задачу.

## Принятие кандидата

Принять максимум один замороженный hash к контрольному прогону. Передать его
Ерлану вместе с baseline. До результата не объявлять победу и не подменять CSV.

Применить критерии общего плана: технические проверки проходят; средний net не
хуже; убыточных прогонов меньше; среднее худших 10% не хуже, на обоих наборах.
Это консервативный критерий команды, не статистическая гарантия. Если критерии
не выполнены либо времени нет, принять README/проверки, а стратегию сохранить.
Не смешивать несколько непринятых экспериментов в последний момент.

Интеграцию, коммиты, push и сдачу выполнять в пределах конкретного разрешения
оператора и AGENTS.md; планирование само по себе не означает их выполнения.
Сохранять авторство участников.

## После выбора версии

1. Получить документацию Ерлана и при необходимости принятый commit Бауыржана.
2. Зафиксировать интеграционный hash. Если поменялся код, повторить необходимые
   unit-тесты и короткую интеграционную проверку именно этого hash; не перезапускать
   бесконечно все 100 seed после чисто документальных коммитов.
3. Сгенерировать финальный CSV официальным make_submission.py и сравнить с
   повторной генерацией. Старый CSV от другой стратегии не оставлять.
4. Проверить agent.py, strategy/, requirements.txt, README, submission.csv и
   нужные локальные данные для демонстрации. Данные/ключи в Git не добавлять.
5. Обновить HACKATHON/PLAN и активные статусы, убрать выполненные пункты из
   текущих приоритетов. README обновляет Ерлан.
6. Пройти пятиминутное демо: Ерлан — запуск и метрики, Бауыржан — механизм
   решения, Нурсултан — задача, компоненты и ограничения/сдача.
7. После разрешённой отправки сохранить подтверждение платформы, время и
   отправленную версию. Сам git push не равен отправке решения.

## Готово, когда

Есть выбранный hash, совпадающие код/README/CSV, опубликованные агрегаты
проверки, сохранённый вывод демо и фактическое подтверждение сдачи. Если сдача
не выполнялась, это прямо написано в итоговом статусе.

```text
Сначала проверь AGENTS.md, CONTROL, актуальный main, дерево и реальный дедлайн.
Сохрани рабочий baseline 4272a07. При наличии времени выдай новые задачи/revision:
Ерлану — независимая оценка и README, Бауыржану — максимум два эксперимента strategy.
Назначь общую исходную базу, ветки, критерии и новый контрольный диапазон заранее.
Не меняй чужие пути, не возобновляй расписания автоматически. Координируй передачи
по точным hash. Принимай только независимо проверенный кандидат; иначе оставь
baseline и заверши документацию/комплект. Объединение, push и отправка — только
в пределах действующего разрешения оператора. Не выдавай git push за сдачу.
```
